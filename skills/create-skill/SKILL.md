# create-skill — スキル作成・更新

ユーザーの要件から日本語の SKILL.md を作成・更新し、実行中の環境で
利用できる場所へ配置します。OpenCode / Senpi (OMO Native) の設定や
公開されているツールに合わせて、配置とレビューの方法を決めます。

## 1. 要件を確認する

依頼文、起動時に渡された引数、会話履歴から次を整理します。

- スキル名、説明、対象となる依頼。
- 入力、期待する結果、実施する処理。
- 必要なツール、依存関係、権限、ユーザー確認が必要な操作。
- 対象の実行環境、配置先、新規作成か既存スキルの更新か。

既に分かっている内容は再質問しません。不足が作業に影響する場合だけ、
利用可能な質問ツールまたは通常の会話で確認します。
質問や進捗管理のために特定のツール名を必須にしません。
進捗ツールが使える場合は、要件確認・生成・レビュー・検証を管理します。

名前は小文字の英数字とハイフンで構成し、64 文字未満にします。
説明は「何をするか」と「いつ使うか」が分かる短い文にします。
汎用という理由だけで、特定環境のツールや依存関係を隠しません。

## 2. 配置先を決める

ユーザーが指定した配置先と対象環境を優先します。
それ以外は、ロードされたスキルの位置、実際の起動設定、実行中の harness の
設定から、どのディレクトリをスキルとして読み込むか確認します。
別の harness のディレクトリが存在するだけで、それを配置先に選びません。

候補は次の通りです。存在だけで読み込み可能と判断しないでください。

| 用途 | 配置先の候補と確認方法 |
|------|------------------------|
| OpenCode のユーザースキル | `$OPENCODE_CONFIG_DIR/skill`、`$XDG_CONFIG_HOME/opencode/skill`、`~/.config/opencode/skill`。設定された変数と実行中の loader の対応を確認する |
| Senpi のユーザースキル | 起動設定で選ばれた agent directory の `skills`。環境変数やデフォルトは使用中の Native 版の設定を確認する |
| プロジェクトのスキル | Git ルートの `.agents/skills`、または対象 harness のプロジェクト設定。Git 外では対象プロジェクトのルートを確認する |
| dotagents の配布元 | ユーザーが対象にした dotagents リポジトリの `skills` |
| その他 | ユーザーの指定先が対象環境で読み込まれるか確認する |

Senpi の agent directory は OpenCode の設定ディレクトリから推測しません。
起動設定や、設定されている `OMO_CODING_AGENT_DIR` などの環境変数を確認します。
どの環境にも同じ変数やパスがあるとは仮定しません。
配置先が確定できない場合は、候補と確認できた事実を示して質問します。
複数の場所への同時配置はユーザーが求めた場合に行います。

配布元とインストール済みコピーを区別します。Nix 管理のコピーなど、
更新が消える場所を直接編集せず、管理元の変更が依頼範囲に含まれるか確認します。
dotagents に追加する場合は README の分類規約を読み、
`nix/skills.nix` に適切な分類を登録します。追加しただけで `generic` にしません。

## 3. 生成・配置する

基本形式は次の通りです。見出しの数や手順は必要な内容に合わせます。

```markdown
---
name: example-skill
description: "対象となる依頼と、実行する処理の短い説明。"
---

# スキルの目的

入力と期待する結果、実施する手順、必要な制約を日本語で記述する。
```

生成時は次を守ります。

- `name` をスキルディレクトリ名と一致させ、正しい YAML frontmatter を書く。
- 本文は日本語とし、コードブロックには言語を指定する。
- 実際に利用できるツール名と公開 schema を使う。存在しない API を作らない。
- 環境依存の操作は対象環境と確認方法を示す。固定パスが不要なら相対参照を使う。
- ユーザーの指定した範囲・権限を保ち、依頼にない設定変更や外部操作を追加しない。
- 説明は簡潔にし、同じ手順や進捗更新の例を繰り返さない。

利用可能なファイル操作ツールで `<配置先>/<name>/SKILL.md` を書き込みます。
既存ファイルがある場合は先に読み、更新依頼の範囲を反映して変更します。
新規作成の依頼で同名スキルが見つかった場合は、上書きせず扱いを確認します。
書き込みに失敗した場合は、原因を報告し、依頼範囲内の修正や配置先変更を検討します。

## 4. レビューと修正

現在公開されている `task` の schema と、ロード済みの agent / category を確認し、
スキルをレビューできる役を選びます。OpenCode で Oracle が利用可能なら使えます。
Senpi (OMO Native) に Oracle が存在するとは仮定しません。
利用可能な reviewer がなければ、同じ基準で自己検証し、レビュー未実施を報告します。

レビューには、ユーザーの要件、生成ファイルの内容または読める位置、次の基準を渡します。

1. frontmatter、名前、説明、参照ファイルが正しいか。
2. ユーザーの目的と対象環境に合うか。
3. ツール名、呼び出し方法、配置先が実環境で利用可能か。
4. 権限とユーザー確認の境界を守り、失敗時の対応が明確か。
5. 手順の不足や重複がなく、スキルを読んで実行できるか。

指摘に基づく修正と再レビューは最大 3 回行います。
継続は公開 schema が示す方法と実際に返された ID / 名前を使います。
OpenCode の `task` や Native の `task_send` などは版によって引数が異なるため、
固定の呼び出し例を流用せず、使用中のツールの説明に従います。
ID の形式を推測したり、他環境の引数名を流用したりしません。
継続機能がなければ、更新内容を渡して新しいレビューを依頼します。

レビューの起動に失敗した場合は公開 API と設定を確認します。
利用できなければ自己検証へ切り替え、実施できなかった内容を報告します。
3 回の修正後も問題が残る場合は、その内容を報告して追加の対応を相談します。

## 5. 検証と報告

配置後にファイルを読み直し、frontmatter、名前、コードブロック、参照先を確認します。
対象環境の検証・ロード機能が利用可能なら、その公開された方法で確認します。
runtime のロードを試していない場合は、確認済みと報告しません。

完了時はスキル名、作成・更新した実際のパス、検証方法、レビュー結果を伝えます。
修正した主な問題、残存問題、未実施の確認があれば明記します。
追加ファイルや別環境への配布は、ユーザーが求めた範囲に合わせます。
