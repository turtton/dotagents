# Worktree PR

Git と対象ホスティングの CLI または API を使う。特定のエージェント、質問ツール、追加スキルには依存しない。
リポジトリの規約とユーザーの指定を優先する。「PR 作成まで」などの制限があればそこで完了する。

## 1. 作業場所を確定する

- 作業対象、ベースブランチ、remote、既存 PR を確認する。不明点が実装に影響する場合だけ質問する。
- `git status --short`、`git worktree list --porcelain`、`git rev-parse --git-common-dir` で現在の変更と worktree 構成を確認する。
- 元のプロジェクトルートを特定し、作業場所を `<project-root>/.worktrees/<task>` とする。
  linked worktree 内の `git rev-parse --show-toplevel` はその worktree を指すため、元のルートとして使わない。
- 同じタスクの worktree・ブランチ・PR があれば再利用する。別タスクを始める場合も元のルート配下へ作成し、`.worktrees` を入れ子にしない。
- `<task>` はパス区切りを含まない短い名前にし、既存パスやブランチを上書きしない。
- 元の作業ツリーの変更は保持する。明示依頼なしに移動、stash、reset、コピーしない。
- `.worktrees` が ignore 済みか確認する。未設定なら共通 Git ディレクトリの `info/exclude` に `/.worktrees/` を追加し、追跡中の ignore ファイルは変更しない。
- ベースの remote ref を更新し、規約に沿ったタスクブランチと worktree を作る。以後の編集・検証・コミットはその worktree 内で行う。

```sh
git worktree add -b <branch> <project-root>/.worktrees/<task> <base-ref>
```

## 2. PR を作成する

1. 依頼範囲の実装を行い、リポジトリ指定の検証と変更に対応するテストを実行する。
2. 差分をレビューし、無関係な変更や秘密情報を含めず、対象ファイルだけを stage してコミットする。
   コミット規約と hook を守り、失敗した hook を無効化して進めない。
3. タスクブランチを push し、意図した remote・base・head で PR を作成する。既存 PR があれば更新する。
4. PR のタイトルと本文に、問題、変更後の挙動、検証結果、未検証事項を記載する。
5. PR URL、base/head、最終 head SHA、作業パス、検証結果、現在の CI 状態を確認して提示する。

push や PR 作成が認証・権限などで止まった場合は、完了済みの作業と再開方法を報告し、ブランチと worktree を保持する。

## 3. マージの許可を確認する

PR を作成してレビュー可能にした後、具体的な PR URL、変更概要、検証結果、CI 状態を添えて、
「CI が通ったらこの PR をマージしてよいですか」とユーザーに質問する。
マージの許可には、マージ確認後に当該作業 worktree と関連する local・remote ブランチを安全確認のうえ削除することも含まれると説明する。
当該 PR のマージについて既に明示許可がある場合は再質問せず、後片付けについても別の許可を求めない。
マージ方式はユーザー指定またはリポジトリ規約に従い、どちらでも決まらなければこの質問で確認する。

- 返答待ち・未承認・拒否の場合はマージしない。auto-merge の予約も行わない。
- worktree やブランチを保持するようユーザーが明示した場合は、その指定を優先する。
- PR 作成だけの依頼ならマージ許可を求めず完了する。
- CI がない場合は合格扱いにせず、「CI がない」事実を伝えたうえでマージの明示許可を得る。
- PR の未解決レビュー、保護ルール、権限などを迂回しない。

## 4. CI を確認してマージする

1. PR の最新 head SHA に対する必須 check と対象 CI が成功したことを確認する。
   pending、失敗、キャンセル、結果不明は合格にしない。古い SHA の成功結果は使わない。
   CI がない場合だけ、前節で得た「CI なしでマージする」明示許可を CI 条件とする。
2. CI の失敗が依頼範囲で修正できれば修正・検証・コミット・push し、新しい head の結果を確認する。
   範囲外の修正、権限不足、外部障害などで進められなければ原因を報告し、PR・ブランチ・worktree を保持する。
3. 明示許可、CI 条件、レビュー条件が揃ったら、マージ直前に head と CI を再確認して指定方式でマージする。
   許可後に変更概要やリスクが変わる追加変更をした場合は、更新内容を示して許可を取り直す。
4. queue や auto-merge への登録はマージ完了ではない。ホスティング側の PR 状態が `merged` になるまで確認する。
   待機を続けられない場合は予約状況を報告し、後片付けせず状態を残す。

## 5. マージ確認後に後片付けする

- ホスティング側で当該 PR の `merged` と最終 head SHA を確認してから削除に進む。
- 対象 worktree の dirty・untracked ファイル、PR 最終 head 以降の追加コミット、別 worktree の同ブランチ利用を確認する。
  いずれかがある場合や branch head が PR 最終 head と異なる場合は削除せず、残した理由とパスを報告する。
  関連のない worktree やブランチには触れない。
- 元のプロジェクトルートへ移動し、`git worktree remove <task-path>` で対象だけを削除する。
  `remove --force` や `rm -rf` は使わず、削除が拒否されたら状態を保持する。
- local branch は `git branch -d <branch>` で削除する。
  squash/rebase マージ後に `-d` が拒否された場合だけ、PR が merged、branch head が PR 最終 head と一致、追加変更なしと再確認した対象に限り `-D` を使える。
- remote branch は現在の head が PR 最終 head と一致することを確認して削除する。
  確認後の追加コミットも削除しないよう、期待する SHA を条件にした原子的な削除を使う。
  Git なら `git push --force-with-lease=refs/heads/<branch>:<pr-head-sha> <remote> :refs/heads/<branch>` とし、拒否されたら保持する。
  ホスティング側で既に削除済みならそのままでよい。
- 最後に PR URL、マージ結果、検証・CI 結果、削除したもの、保持したものを報告する。
